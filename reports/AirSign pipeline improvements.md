# Improve AirSign Without Breaking Recognition

AirSign can get smoother without changing what the ASL model sees: first measure the full frame-to-result path, then move ONNX WASM work off the UI thread and evaluate a MediaPipe worker with the same models, inputs, and decision rules. The largest likely responsiveness cost is synchronous landmark detection on each camera frame; ONNX inference and repeated tensor assembly add more work, but this scan did not measure their share on a real device. Accuracy improvements need their own evaluation: published PopSign and ASL Citizen scores are not AirSign live-camera scores, and the current evidence thresholds have not been calibrated on held-out AirSign signers. Keep the known-good WASM backend, full landmark layout, 1.5-second window, and current thresholds as the reference until a fixed clip set shows a change is both faster and accurate enough.

## Measure each stage before tuning the recognizer

The current ASL Words path receives camera frames at an ideal 35 fps and up to 40 fps, runs `HolisticLandmarker.detectForVideo` synchronously, converts each result into the 543-point model layout, and classifies the latest 1.5 seconds about every 250 ms. At the requested capture rate, that window often contains roughly 52–60 frames. The existing `?debugAsl=1` measurement times ONNX `session.run()` but starts after frame stacking and tensor creation, so it cannot identify whether the delay is Holistic, JavaScript packing, ONNX, or UI rendering. Add sampled p50/p95 timings for callback cadence, Holistic detection, `frameTo543`, buffer assembly, tensor creation, `session.run()`, and time from inference completion to a visible guess. Compare cold and warm model loads separately and run on a lower-end phone and a typical laptop before choosing an optimization. ([AirSign ASL loop](../src/engine/useAslWords.ts), [classifier](../src/engine/asl-classifier.ts), [ONNX Runtime performance diagnosis](https://onnxruntime.ai/docs/tutorials/web/performance-diagnosis.html))

For the ASL recognition baseline, collect a small consented clip set with multiple signers, camera distances, lighting conditions, left/right hand use, transitions, no-sign footage, and signs outside the 250-label vocabulary. Split by signer rather than by frame. Track top-1 accuracy, top-3 recall, macro-F1, per-class confusions, false locks per minute, out-of-vocabulary rejection, and p50/p95 time-to-emission. The PopSign paper reports 82.1% validation and 84.2% test accuracy for its own LSTM and signer-disjoint data split; it also discusses variation in sign variants. Those numbers describe that experiment, not AirSign’s downloaded ONNX model or current camera path. ASL Citizen’s 63% top-1 and 91% recall-at-10 are from a different dataset and task, so they also cannot serve as AirSign’s score. ([PopSign ASL v1.0 paper](https://papers.nips.cc/paper_files/paper/2023/file/00dada608b8db212ea7d9d92b24c68de-Paper-Datasets_and_Benchmarks.pdf), [ASL Citizen paper](https://arxiv.org/abs/2304.05934))

## Offload computation while preserving the current result path

The lowest-risk runtime experiment is ONNX Runtime’s WASM proxy worker. It moves WASM computation away from the UI thread and is documented as a responsiveness improvement, not a guaranteed reduction in model inference time. Keep the same 22 MB model, WASM provider, full `[T,543,3]` input, and current result confirmation rules; measure UI frame delay and end-to-end time as well as `session.run()`. Check the deployed Content Security Policy because proxy mode creates a worker from a Blob. This is a smaller change than moving camera tracking and should be tested first. ([ONNX Runtime proxy worker guidance](https://onnxruntime.ai/docs/tutorials/web/performance-diagnosis.html), [ONNX Runtime environment flags](https://onnxruntime.ai/docs/tutorials/web/env-flags-and-session-options.html))

If Holistic timing dominates, prototype a dedicated MediaPipe worker for ASL Words. MediaPipe documents synchronous video recognition as UI-blocking and recommends workers for camera video; Google’s web samples include a Holistic worker using the current Tasks Vision 1.2.x family. This supports feasibility, not a proven AirSign speedup. Send transferable frames, keep at most one frame in flight, drop stale frames in favor of the newest frame, preserve increasing timestamps, and retain the existing main-thread fallback. Keep the current model, landmarks, camera request, and thresholds fixed during this comparison so the experiment measures execution location rather than changing recognition. ([MediaPipe Gesture Recognizer for Web](https://developers.google.com/edge/mediapipe/solutions/vision/gesture_recognizer/web_js), [Google Holistic worker sample](https://github.com/google-ai-edge/mediapipe-samples-web/blob/main/src/workers/holistic-landmarker.worker.ts), [worker base implementation](https://github.com/google-ai-edge/mediapipe-samples-web/blob/main/src/workers/base-worker.ts))

## Tune WASM threads only when hosting supports them

AirSign currently fixes ONNX Runtime WASM to one thread. ONNX Runtime supports automatic thread sizing, but WASM multithreading requires browser support and cross-origin isolation. That isolation uses COOP/COEP headers, and COEP can block external resources that do not opt in. The repo’s current ASL ONNX and WASM assets are self-hosted, but every other external asset and deployment path still needs checking. Test `numThreads = 0` or a small thread count behind a capability check, compare CPU contention with MediaPipe, and keep the one-thread fallback. Do not assume more threads are faster on a phone. ([ONNX Runtime environment flags](https://onnxruntime.ai/docs/tutorials/web/env-flags-and-session-options.html), [WASM API reference](https://onnxruntime.ai/docs/api/js/interfaces/Env.WebAssemblyFlags.html), [web.dev COOP/COEP guide](https://web.dev/articles/coop-coep))

The recent WebGPU attempt regressed AirSign’s ASL Words behavior, and another project using the same dynamic-time Kaggle model reports that WebGPU was much slower there. That report is not a general rule, but it reinforces the current decision to keep ASL Words on WASM. WebGPU graph capture is also aimed at static shapes with operators placed on WebGPU, while AirSign’s time dimension varies with the camera cadence. Revisit WebGPU only as an isolated A/B test after profiling node placement and preserving a measured WASM baseline. ([AirSign runtime](../src/engine/ort.ts), [ONNX Runtime WebGPU guidance](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html), [project report on this model](https://github.com/nlevites/signchat/blob/main/ARCHITECTURE.md))

## Change temporal input only against held-out clips

AirSign’s full 543-point frame contains face, pose, and both hands because the current classifier consumes that layout. Removing face or pose data risks changing the model’s features, so it is not a safe first optimization. The same caution applies to reducing sequence length: a 48-frame cap is a useful test candidate because the current 1.5-second window can reach about 52–60 frames, but another project’s cap does not prove that AirSign will retain accuracy. Compare the full window with uniformly sampled 48- and 32-frame inputs on the same signer-held-out clips. Keep NaN handling, frame order, thresholds, and confirmation behavior fixed; only ship a shorter input if latency improves and accuracy, false-lock rate, and time-to-emission stay within agreed bounds. ([AirSign frame layout](../src/engine/holistic-frame.ts), [ASL word window](../src/engine/useAslWords.ts), [same-model project report](https://github.com/nlevites/signchat/blob/main/ARCHITECTURE.md))

Confidence tuning belongs after that baseline. AirSign currently accepts a gloss based on repeated top-two support across overlapping windows and fixed average/peak floors. Overlapping predictions are correlated, not independent votes. Evaluate false acceptance on no-sign, transition, and out-of-vocabulary footage before changing those constants. Softmax values are not automatically calibrated probabilities; temperature scaling is one post-hoc calibration method, but it must be fit on validation data and evaluated on separate held-out data. ([AirSign confirmation rule](../src/engine/useAslWords.ts), [Guo et al. on calibration](https://proceedings.mlr.press/v70/guo17a.html))

## Recommended order keeps working behavior as the baseline

Start by adding opt-in stage timing and recording the current latency and recognition metrics. Next test ONNX proxy mode with unchanged inputs, then test a MediaPipe worker with latest-frame back-pressure if tracking is the dominant cost. In a separate branch, test WASM threading only on cross-origin-isolated builds. Finally, use the labeled clips to evaluate temporal sampling, quantization, or confidence changes one at a time. Preserve the known-good WASM configuration and provide a fallback for each runtime experiment; do not merge a speedup based only on a higher FPS number if false guesses increase or the time-to-guess worsens.

The key distinction is between smoother interaction and more accurate recognition. Workers can reduce main-thread blocking without changing the model’s decisions, while sampling, quantization, delegates, thresholds, and landmark changes can alter predictions. AirSign has promising paths in both directions, but its next improvement should be a repeatable benchmark that makes those tradeoffs visible rather than another unmeasured model tweak.
